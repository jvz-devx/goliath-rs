# E13. Crashes and partitions on the real cluster

## Result

The complete 1,000-seed crash schedule passed recovered item accounting, with
zero duplicate or missing named items. M3 is not complete. Two real-process
fencing defects remain. This is implementation evidence; review
and milestone decisions are separate.

Two fencing tests have failed. A live tile with a replaced store fence can still
append cuts and accept an ordinary returning login. Delayed and replayed player
CAS requests and explicit `player-import` placement are rejected, but those
checks do not fence the world log or normal returning-player placement.

The launcher now replaces dead tiles without restarting healthy tiles or the
proxy. A real restart, reconnect and subsequent crossing passed at light load.
The store and proxy were each killed once during a crossing. Recovered named
item totals matched. Four old abort requests were rejected after two crossings.

This work uses the retained executables in `.local/bin/goliath-e10/`, not E12.
No Horizon, Meridian or store source was changed. No build, commit, push or
upstream operation ran. No Folia, Paper, GPL source or excluded research was read.
Other agents' changes in the shared worktree are outside this experiment.

## Fault method

Every trial starts four real Horizon processes, the fenced store, Meridian and
four sidecars in fresh private homes and XDG directories. All sockets are on
loopback with dynamically allocated ports. Every run directory lives under
`.local/runs/` and is removed after extracting results. Prepared 26.3 game
resources are only read. No launcher management command runs.

One walking client takes seven uniquely named diamonds from a chest with real
menu clicks. Its previous coherent cut contains those seven in the chest and
an empty player inventory. Eleven differently named diamonds stay in the chest.
A uniquely named unpickable emerald drop contains thirteen. The seed appears
in each name. The take is not checkpointed again before the crossing fault.

This catches rollback that restores a source chest beside a committed incoming
inventory. The eleven-item chest and thirteen-item drop are durable controls.
They do not exercise a dirty donor inventory or a concurrent drop/pickup chain.

The harness blocks exact existing process gates, not an estimated sleep before
a disk operation. The two network gates forward real requests and responses.
They never fabricate a successful reply.

| Step | Deterministic gate | Meaning |
| --- | --- | --- |
| Write | `mid-append` | Half of the source cut frame has been written. |
| Fsync | `head-rename` | Complete append, immediately before the full file barrier. This legacy gate name does not mean a rename happens here. |
| Install | `installed` | Full barrier and worker head update finished, before the cut request returns. |
| CAS | TCP response held after store `CommitUuid` | Generation one is durable. The proxy has not received its response. |
| Acknowledgement | Control response held after `player-import` | Target placement succeeded. Its acknowledgement has not reached Meridian. |

The fault victim is the source, target or both. A seeded shuffle covers each
of the fifteen combinations once per block, then repeats. The complete schedule
is saved before execution. A failed seed stops new submissions; already running
trials finish and retain their evidence. Each trial has its own world and item
names. This is 1,000 independent attempted crossings, not 1,000 uninterrupted
crossings in one long-running world. Faulted crossings use a to b. This is not
another all-border-direction matrix.

After each fault the harness allows the immediate error paths to execute, kills
the remaining tile processes without a clean cut, restarts each under a new
fence and inspects its actual recovered files while stopped. The checker counts
named stacks in every current player file, every saved block entity and every
saved entity across all tiles. It reads the store too. The store entry is an
anchor, not an additional item copy. It counts escrow only if no matching owner
player file exists. Departed or wrong-generation current player files fail the
check. Historical `.dat_old` fallback files are not counted by this E13 checker.

This is SIGKILL evidence, not power-loss evidence. Unsynced writes in the kernel
cache may survive a process kill. E9's file-cache-loss controls remain separate.
No SIGKILL sample proves a disk controller honored a barrier.

The pre-barrier `fsync` gate often restores the complete appended cut, although
the caller never received its receipt. The simulator instead discards the
unflushed suffix on a crash. Both preserve identities here, but may roll back
different progress. The half-written frame at the write gate restores the old
chest image. Do not label the full-frame SIGKILL behavior a power-loss test.

## Defect E13-1. Store ownership does not fence the cut writer

High severity. Reproduced with seed 13001. Evidence is
[`data/E13/partition-process-13001.json`](data/E13/partition-process-13001.json).

```sh
python3 -B scripts/m3-chaos partition --seed 13001 --name partition-reproduction
```

This exits 1 on the retained E10 binaries. Use a new `--name` for another run;
the harness refuses to overwrite evidence.

The reproduction does this:

1. Tile a owns store fence `0:1:1`. It makes durable cut sequence 3.
2. A new cut captures and blocks at `pack-sync`, before taking the append lock.
3. A controllable TCP proxy isolates a from the store. The old process stays
   alive. Existing registered players do not need a store call each tick.
4. A separate real Horizon process starts for tile zero with its own private
   world and cut directory. Its claim gets fence `0:5:2`; its bootstrap cut
   succeeds. This isolates fencing from shared-file convenience. It is not a
   claim that the replacement recovered the old world's data.
5. The queued old cut resumes and succeeds as sequence 4. A fresh old-process
   cut succeeds as sequence 5 while partitioned. After healing, another succeeds
   as sequence 6. The old local `FENCE` file still contains `1:1`.
6. An old-fence player CAS and its exact replay both return `010501`, stale
   fence. The player's generation and owner remain zero. Placement through the
   stale process returns `stale cluster tile fence`.

The queued stale append wrote 11,487 bytes. The next two wrote 11,436 each.
The old process advanced from tick 66 to tick 82 while the replacement started.
This is an accepted, flushed old-owner write, not just a stale read or log line.
It does not by itself demonstrate duplicated items.

The E10 cut writer's fence check reads only the local `FENCE` file. See
`patches/horizon-01-tile-cut.patch`, added `tile_cut/store.rs`, `fence` and
`Writer::append`, around patch lines 1274 and 1513. The cluster integration
checks the store fence for recovery and activation, but does not connect that
directory to local cut append authorization.

The smallest safe fix needs one authority ordering for ownership replacement
and cut append/install. A replacement must revoke the old writer at the actual
storage boundary, or wait for a lease that prevents old writes before becoming
active. A store lookup before append alone leaves a claim/append race. Updating
one local file in the normal dead-process launcher is not fencing an isolated
process with a separate storage path. This fix belongs to Horizon/store
integration. This test agent did not change it and stopped that line of work.

## Defect E13-2. A replaced process accepts an ordinary returning login

High severity. Reproduced independently with seed 13801. Evidence is
[`data/E13/stale-login-13801.json`](data/E13/stale-login-13801.json).

```sh
python3 -B scripts/m3-chaos stale-login --seed 13801 --name stale-login-reproduction
```

This exits 1. The fixture logs out its registered player after a durable cut,
isolates tile a from the store and starts a real replacement with fence `0:5:2`.
It heals the connection and reconnects the same client through the existing
Meridian route. That route still addresses the old process. A stale route must
not grant placement authority to a replaced backend.

The directory confirms current process 5, epoch 2. The old process still has
process 1, epoch 1, yet `transfer-status` reports `players=1`, `online=1`,
`frozen=0`, `held=0`. Its player export contains all seven named carry items.
The client receives its teleport, regular movement events and inventory data.
This is an ordinary returning login, not a forged `player-import` request.

The registration filter in the E10 integration only sends players without a
local `goliath:generation` to `CreateUuid`. A returning saved generation-zero
player bypasses that call and its fence check. See
`patches/horizon-03-cluster.patch`, added `dedicated/cluster.rs`,
`cluster_register_players`, around patch line 393. Explicit activation calls
`current` first, but this ordinary login path does not.

The smallest proposed fix is to require a current process fence at every normal
player placement boundary, including loaded returning players, and fail closed
before that player can act. Keep generation-aware local inventory recovery;
resetting a matching player from the older store entry would create a different
P5 bug. Fixing only proxy manifest refresh leaves stale routes unsafe. No source
fix was attempted and no further ordinary-login fencing trials ran.

## Tile supervision

`goliath-cluster start` now checks for dead tiles every 250 ms. A replacement
keeps its game port, claims a new fence, recovers against the store, verifies its
world marker and completes its bootstrap cut before the launcher atomically
publishes its new endpoint and fence. Sidecars already reread their endpoint
files. Meridian reads the cluster manifest for new controls, so the proxy and
healthy tile processes stay running.

A death racing a periodic background cut is handed to the next supervision
iteration. A cut error from a still-running process still fails closed. A
failed startup/recovery leaves that tile unavailable and retries with one to
five seconds of backoff. It does not publish the failed replacement or stop
healthy tiles. The retry/quarantine branch has an offline control test; the
real-process restart measurement below had no startup failure.

The final seed-13101 check replaced tile a in 0.589 seconds. The client was
disconnected by the dead backend, then the test client reconnected without any
server restart command. Its nine named diamonds survived and its next crossing
committed generation one. The proxy PID, the other three tile PIDs and the dead
tile's game port did not change. This tests automated server recovery and a
scripted client reconnect, not automatic reconnect behavior in a stock client.

There are 63 healthy-tile TPS samples, 21 per tile, spanning the restart and
subsequent crossing. Target TPS is 20. The reported five-second-window values
range from 19.979 to 20.034. This is a light-load continuity check, not a capacity
test or a guarantee about every future crash. See
[`data/E13/supervisor-final-13101.json`](data/E13/supervisor-final-13101.json).

`goliath-cluster --store-binary PATH` selects a different store executable for
start/proof/items/walking. Its default remains the retained E10 store. Proof
evidence hashes the selected executable, not the default. The reviewer can run:

```sh
python3 -B scripts/goliath-cluster proof --crossings 14 \
  --store-binary .local/bin/goliath-store-e15-d4d84912bcd1/goliath-store \
  --name e15-store-proof
```

The option's default/override dispatch has an offline test that starts no
process. E13 did not run the E15 executable.

## Comparison with E1 and E9

| Fault class | P5 prediction | E13 observation |
| --- | --- | --- |
| Source dies before a complete durable cut | Abort the crossing and restore the earlier coherent source state. A taken item may return to its chest without being lost. | All 200 write and 201 fsync trials conserved the items. The 133 partial-frame source/dual kills restored the take to the chest. Complete cached frames may survive SIGKILL, as explained above. |
| Source dies after its cut | The durable source cut supports a later fenced CAS, or recovery retains the source if CAS never committed. | All 201 install trials conserved the items. Matching local progress survived even when the store entry was older. |
| Target or both tiles die after CAS | The committed entry is authoritative escrow until the target materializes it. | All 398 CAS/ack trials retained generation one at b and conserved the items, including the target and dual kills. The separate infrastructure tests also recovered correctly. |
| Replayed old abort | Must not resume a departed or newer handover. | Four old requests rejected after two real crossings. |
| Stale process after ownership replacement | Stale CAS, cut append and player placement must fail. | CAS and explicit import fail correctly. Cut append and ordinary returning placement do not. These violate model assumptions. |

E1/E9 assumed fencing at the log boundary and one current authorized process.
E13-1 and E13-2 show that the integration does not supply those assumptions.
Zero duplication in the crash matrix cannot repair that mismatch. The simulator
does not predict real TPS or restart latency.

Twenty new offline/loopback checks and eight existing E10 evidence checks pass.
The new checks catch planted same-tile duplication, item loss, lost committed
generation, stale current player files and a wrong phase gate. Before/after TCP
gates preserve the real request bytes and hold delivery at the requested side.
Live log parsing ignores incomplete final lines.
Quiet-window controls check both draining active trials before acknowledging and
the 40-minute limit, without starting an engine.

Two initial harness failures remain in the data. `partition-13001.json` exposed
a missing-file race while waiting for the phase marker. `supervisor-13101.json`
and `write-source-13201.json` exposed macOS `killpg` returning EPERM for an already
reaped test-client group. Those are harness failures, not product duplication.
Their replay files are separate. The launcher now avoids signaling an already
dead child and handles that exit race without hiding failures from a live child.

The original campaign stopped at 576 attempts. Seeds 14572 through 14575 failed
during initial store claims with macOS `EADDRNOTAVAIL`, before any fault gate.
Their retained files are failures, not conservation samples. A subsequent
loopback connection check and the unchanged seed-14572 replay passed. A later
sample showed 35 TIME_WAIT sockets; port exhaustion was not established. The
cause of the transient connect failures remains unknown.

The failure also exposed an E13 cleanup path that assumed every tile had started
a server. Cleanup and failure-tail collection now accept an unstarted tile.
The original failed summary and every failed seed remain. The resumed campaign
uses the exact original 1,000-seed schedule, retains its 572 successful rows and
replays the four pre-gate failures before the unstarted remainder. It does not
change a fault point, victim or binary to obtain a pass.

E13 honored E15's quiet windows at natural trial boundaries. Active clusters
finished, the campaign paused, `.local/quiet-ack-E13` was created and no E13
cluster process remained. The acknowledgement was removed and trials resumed
when each request disappeared. Trial boundaries check the same protocol, with
the requested 40-minute maximum wait. A reservation check also prevents a new
request from racing binary hashing or engine startup.

No Cargo command ran. The reviewer owns workspace gates and builds against the
